## 0. 环境事实（V0.2 开工前实测）

| 项 | 实测结果 | 对实现的影响 |
| --- | --- | --- |
| `/v1/embeddings` | vlm_server(8080) 与 geniex serve(18181) **均 404** | 本地无现成 embedding 端点 |
| AI Hub 模型列表 | qcs8275 无任何 embedding 模型（只有 llm/vlm） | 短期拉不到 NPU embedding 模型 |
| numpy | **未安装** | 向量运算用纯 Python（array/struct），个人库规模（千级向量×384维）足够快 |
| sqlite-vec | 未安装 | 向量存 BLOB float32，暴力 cosine 扫描 |
| 磁盘 | 27 GB 可用 | 不构成约束 |

**结论（关键取舍）**：V0.2 的 embedding 层做成 **可插拔 Provider**：

1. `ngram`（默认，确定性）：字符 2/3/4-gram 哈希 → 384 维 L2 归一化向量。纯 CPU、零依赖、毫秒级。
   **如实声明**：这是词法模糊相似（召回增强），**不是**真语义向量——但把向量基建（表、cosine、RRF 混合、增量回填）全部打通。
2. `openai`（可选）：任何 OpenAI 兼容 `/v1/embeddings` 端点（未来 GenieX 支持、或云端）。配置 `KC_EMBED_*` 即自动启用，无需改代码。
3. **真语义**由可选 **LLM rerank** 提供（对 top-N 候选打分重排），复用本地 qwen3-4b。

这符合提案 Principle 3（CPU first）与 Principle 9（不过度建设）。

## 1. V0.2 范围

**做：**

1. **Embedding 层**：`EmbeddingProvider` 接口 + `ngram`/`openai` 双实现；`embeddings` 表（chunk/claim 级）；`kc embed` 增量回填（按内容 hash 跳过已算）
2. **Hybrid Search**：FTS(bm25) + LIKE + vector(cosine) + **entity-hop**（实体→提及文档→相关 claims/chunks）四路召回 → **RRF**（Reciprocal Rank Fusion）合并 → 可选 LLM rerank
3. **Entity Resolution**：`entity_aliases` 别名表；确定性归并（norm 精确/别名命中）；`kc entities` 列出/`--suggest`（LLM 聚类建议）/`merge`（合并归一）；编译时自动链接
4. **Claim Dedup**：新 claim 入库时取相似候选（FTS+向量）→ LLM 判定 `duplicate / update / contradiction / new`：
   - duplicate → `status='duplicate'` + `duplicate_of`，不入检索
   - contradiction → 旧 claim `status='superseded'` + `superseded_by` + `superseded_reason`（**保留认知演化史**，提案 §17）
   - `kc dedup [--dry-run]` 全库离线整理
5. **Source Citation 强化**：`ask` 的 [n] 引用细化到 claim#/chunk# + 文档 + 位置；`kc show` 输出 claim 的完整溯源链（claim → source 文档 → 原文片段）

**不做（V0.3+）：** Knowledge Graph 存储、矛盾自动巡检、daily digest、backlinks、Memory 层。

## 2. Schema 迁移（v1 → v2，`PRAGMA user_version`）

```sql
-- 新增
CREATE TABLE embeddings (
  id         INTEGER PRIMARY KEY,
  scope      TEXT NOT NULL,            -- 'chunk' | 'claim'
  ref_id     INTEGER NOT NULL,         -- chunks.id / claims.id
  model      TEXT NOT NULL,            -- 'ngram-v1' | 端点模型名
  dim        INTEGER NOT NULL,
  vec        BLOB NOT NULL,            -- float32 little-endian
  content_sha TEXT NOT NULL,           -- 被嵌文本的 hash（增量判断）
  UNIQUE(scope, ref_id, model)
);
CREATE TABLE entity_aliases (
  alias_norm TEXT PRIMARY KEY,         -- norm(alias)
  alias      TEXT NOT NULL,
  entity_id  INTEGER NOT NULL REFERENCES entities(id) ON DELETE CASCADE
);
-- claims 增列
ALTER TABLE claims ADD COLUMN duplicate_of INTEGER;      -- 重复指向
ALTER TABLE claims ADD COLUMN superseded_reason TEXT;    -- 矛盾/演化原因
-- documents.id 已有 sha256 → embeddings 增量以 content_sha 为准
```

迁移规则：`db.py` 读 `user_version`，逐版执行幂等 DDL，写回版本号。V0.1 库（version=0）自动升级到 2。

## 3. 模块设计

### 3.1 `vectors.py`（纯 Python 向量）

- `embed_ngram(text, dim=384) -> bytes`：2/3/4-gram 计数 → 哈希桶（带符号哈希防碰撞偏置）→ TF 加权（`1+log(tf)`）→ L2 归一化 → float32 打包
- `cosine(a: bytes, b: bytes) -> float`：`array('f')` 解包点积（已归一化）
- `topk_by_cosine(candidates, query_vec, k)`：暴力扫描（个人库规模足够）

### 3.2 `embed.py`（Provider）

```
EmbeddingProvider.embed(texts: list[str]) -> list[bytes]
  ├─ NgramProvider(model='ngram-v1')            # 默认，离线
  └─ OpenAIEmbedding(base_url, key, model, dim) # 探测 /v1/embeddings 成功才启用
```

- `kc embed`：扫 chunks+claims → 算 content_sha → 无变化跳过 → 批量入库（删除旧 model 向量）
- 编译后自动触发（同一事务外，失败不阻塞编译）

### 3.3 `retrieve.py`（Hybrid + RRF）

```
召回四路：
  A. FTS trigram bm25（词元≥3）
  B. LIKE OR + 命中数（短词兜底）
  C. vector cosine top-k（问题向量 vs embeddings）
  D. entity-hop：问题中出现的实体名/别名 → entity_mentions → 该文档的 claims/chunks
合并：RRF  score(d) = Σ 1/(k + rank_i(d))，k=60
可选：--rerank 用 LLM 对 top-15 逐条打 0-10 相关分，重排
```

`ask` 默认 hybrid；`search --mode fts|hybrid` 可对照。

### 3.4 `entities.py`（Entity Resolution）

- 编译入库：新实体 norm 与 `entities.norm` 或 `entity_aliases.alias_norm` 命中 → 归并到既有实体（提及+计数），否则新建
- `kc entities [关键词]`：列实体（含别名、提及文档数）
- `kc entities --suggest`：取全部实体名 → LLM 分组建议（"Qwen/通义千问/千问 → qwen"）
- `kc entities merge <idA> <idB> [--alias]`：B 并入 A（mentions 转移、别名登记、doc_count 重算）

### 3.5 `dedup.py`（Claim 生命周期）

- 编译时：新 claim 先查 `norm` 精确重复（同库不同文档）→ 直接 duplicate；再取 FTS/vector top-5 候选 → LLM 判定四态
- LLM 提示词（小输出）：
  ```
  判断新论断与候选的关系：duplicate（同一意思）/ update（更具体版本）/ contradiction（矛盾）/ new（无关）
  输出 JSON: {"verdict": "...", "target": 候选编号, "reason": "一句话"}
  ```
- 全库模式 `kc dedup`：active claims 两两批次判定（--dry-run 只打印不写）
- 检索一律 `status='active'`（duplicate/superseded 不入上下文，但 `show` 可看演化链）

### 3.6 `ask`/`show` 溯源强化

- 引用格式：`[n] claim#25｜文档标题｜chunk#12 附近`（claim → 所在 chunk 由同文档 FTS 定位）
- `kc show <doc_id> --claim <id>`：输出 claim 全链（文本/类型/置信度/来源文档/相似 duplicate 列表/superseded 链）

## 5. 验收标准（DoD）

1. 旧 V0.1 库自动迁移（user_version 0→2），数据零丢失（docs/chunks/claims 计数不变）
2. `kc embed` 后 embeddings 覆盖全部 chunks+claims；重复执行全跳过（增量）；同文本 cosine=1.0，近义文本 > 无关文本
3. `search --mode hybrid` 对 V0.1 的三个基准查询结果不劣化，且「个人知识库的核心」类问题召回新增 chunk 级命中
4. `--rerank` 下 `ask` 引用更准（人工核对 top 引用相关性）
5. 实体归并：手工把「通义千问」「Qwen3」别名并进 qwen 实体后，`ask` 提到通义千问能命中 Qwen 相关 claims
6. Claim dedup：构造含重复/矛盾 claim 的文档编译后，duplicate 标记正确、矛盾形成 superseded 链且 `show` 可见演化史
7. 全部回归：V0.1 DoD 七项在迁移后的库上仍通过（init 幂等/编译/检索/ask/增量/降级）
8. 文档同步：本计划状态表、README 状态、issue 关闭

### 实现过程中的设计补充（相对本计划的差异）

1. **ngram 向量规格**：512 维有符号哈希（2/3/4-gram，TF=1+log）。实测近义改写 cosine ≈ 0.41、无关 ≈ -0.04——**排序判别有效但绝对值不高**，所以向量只作为 RRF 的一路投票（贡献排名而非过滤），这比把 cosine 当阈值过滤稳健得多。
2. **迁移需要 v3**：判重增量需要 `claims.dedup_checked` 列，`MIGRATIONS` 版本机制顺带升级（user_version=3）。
3. **实体合并的顺序坑**：必须先删来源实体、再把来源名登记为目标别名，否则 norm 冲突检查会撞到"自己"。别名与目标规范名相同时跳过。
4. **判重判定质量如实记录**：4B 模型的四态判定机制正确、可审计（`show` 输出理由与演化链），但个别语义边界会误判（设计为"矛盾"的样本被判定为"update"）。机制价值 > 单次判定准确率；误判可人工修正（改 status 字段）。
5. **`kc remove` 缺失**：验证判重时需要一个可逆的测试文档，手工清理时踩到 Python sqlite3 默认关 FK、级联不触发的坑（两次删除 documents 行导致子行残留）。干净的 `kc remove <doc_id>`（含级联、孤儿实体清理、演化链保留）列入 V0.3 待办。
6. **编译时长**：判重为每 4 条 claim 一次 LLM 调用（约 30–60s/批），含判重的编译比 V0.1 更慢；`--no-dedup` 逃生舱保留。

## 7. 已知取舍

- ngram 向量是**词法相似**非语义——它的价值是基建打通 + 召回补充 + 未来真 embedding 端点零改动接入（Interface 就是契约）
- LLM rerank 每查询多 ~30–60s（NPU 16 tok/s），默认关闭，按需 `--rerank`
- dedup 的 LLM 判定在编译路径上串行执行会增加编译时长；提供 `--no-dedup` 逃生舱
- 纯 Python cosine 在万级向量时约需 1–2s；到那规模再上 numpy/sqlite-vec（YAGNI）
