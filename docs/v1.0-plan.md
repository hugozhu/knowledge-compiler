# V1.0 实施计划（Personal Knowledge Agent：Context Builder 闭环 + Memory 层 + Web API）

> 依据：[personal-knowledge-base-best-practices.md](./personal-knowledge-base-best-practices.md) 第 13 / 18 / 24 节。
> 前置：V0.1–V0.3 已验收，测试套件（72 用例）全绿。

---

## 0. 定位

V1.0 是闭环的最后一环：知识库的终点不是「搜索」，而是**持续为人和 Agent 生产高质量 Context**（Principle 10）。

```
        Task（任务描述）
            ↓
    Context Builder ──── Memory（动态个人状态，§13）
            ↓
     Task Context Pack（带预算的结构化上下文）
            ↓
    外部 Agent（人 / OpenCode / 云模型）执行
            ↓
    Action → Feedback → kc note（低摩擦回流 inbox）
            ↓
    Knowledge Compiler → 新知识 …（闭环）
```

诚实边界：kc 本身不执行任务；它把「知识 → 上下文」这一步做扎实，执行交给外部 Agent——**Local First, Cloud When Needed**。

## 1. 范围

**做：**

1. **Memory 层**（§13，Knowledge ≠ Memory）：
   - Schema v4 `memories` 表（kind/text/source/confidence/status/created_at/updated_at/**expires_at**）
   - kind：`project / decision / preference / task / discussion / goal`
   - `kc memory add/list/done`；惰性过期（访问时把过期项标 `expired`，**绝不**编译进知识）
   - `ask` 注入活跃记忆（标注 `[记忆]`，与知识引用区分，限额防挤占）
2. **Context Builder**（§18 流程：Task → entities → claims → sources → context）：
   - `kc context "任务描述"`：关键词（LLM，降级分段）→ 实体识别（含别名）→ hybrid 检索 claims/chunks → 活跃记忆 → **预算内**组装 Task Context Pack（Markdown，统一 Sources）
   - `--max-chars`（默认 6000，供大上下文云模型）、`--out <file>`、`--json`（机器可读）、`--no-memory`
3. **Web API**（§19 部署图中的 Web API；零依赖 stdlib `http.server`）：
   - `kc serve [--host 127.0.0.1] [--port 8300]`
   - `GET /health` `/stats` `/search?q=` `/memory`；`POST /ask` `/context` `/memory`
   - 可选 Bearer 鉴权（`KC_API_KEY`，默认本地免鉴权）；LLM 故障 → 503；SQLite 跨线程 `check_same_thread=False` + 写锁
4. **反馈闭环**：`kc note "..."` 低摩擦随手记 → inbox 时间戳文件 → 正常编译回流知识库

**不做：** kc 内置任务执行器、云端编排、多用户/鉴权体系、SSE 流式。

## 2. Schema 迁移（v3 → v4）

```sql
CREATE TABLE IF NOT EXISTS memories (
  id         INTEGER PRIMARY KEY,
  kind       TEXT NOT NULL DEFAULT 'task',
  text       TEXT NOT NULL,
  source     TEXT,
  confidence REAL DEFAULT 0.8,
  status     TEXT DEFAULT 'active',   -- active / done / expired
  created_at TEXT,
  updated_at TEXT,
  expires_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_memories_status ON memories(status, kind);
```

## 3. 验收标准（DoD）

1. memory：add 校验 kind；list 只见 active（过期惰性清理）；done 归档；ask 的上下文含 `[记忆]` 且过期记忆绝不出现
2. context：pack 含 任务/记忆/实体/论断/摘录/Sources 六段；预算被尊重（stats.chars ≤ max-chars）；实体经别名命中；`--json` 可解析；LLM 不可用时降级（确定性关键词+检索）仍出包
3. serve：六个端点行为正确（测试线程内起真实 HTTP 服务断言响应）；LLM 故障返回 503；KC_API_KEY 设置后未带 token 返回 401
4. note：写入 inbox 时间戳文件，compile 后成为知识（claims 进库）
5. `./kc test` 全绿（72 旧用例 + 新用例）
6. 文档同步（README Roadmap → V1.0 完成 / 用法 / AGENTS）+ issue 关闭

### 实现过程中的实测记录（相对本计划的差异）

1. **检索 scope 泄漏 bug（测试驱动 + 真实冒烟双捕获）**：hybrid 的向量与 entity-hop 通道无视 `scope` 参数，导致 `scope="claims"` 时混入 chunk 命中（claim 缺 `type` 字段直接炸 context）。修复后补了 scope 隔离；单测没抓到是因为 FakeLLM 测试数据恰好不触发该路径，真实库冒烟才暴露——**两种验证缺一不可**。
2. **argparse 位置参数陷阱**：`kc memory done 2` 的 `2` 被 `text` 占位吃掉（`mem_id=None`）；`--kind default="task"` 又泄漏给 list 导致默认过滤。修复：`done` 从 text 位兜底解析编号；`--kind` 默认 None、add 时回退 task。
3. **迁移断言泛化**：`test_migration_v0_to_v3` 改为对 `max(MIGRATIONS)` 断言（v4 落地时旧断言即失效）。
4. **serve 线程安全**：SQLite `check_same_thread=False` + 写操作锁；`KC_API_KEY` 未带 token 实测返回 401（有专项测试）。
5. **真实冒烟数据**：`/ask` 6 sources + 1 memory、`/context` 6051 字符 pack、`/memory` 增删闭环，全部通过后清理。
