# V0.1 实施计划（inbox → compile → SQLite/FTS5 → search/ask）

> 依据：[personal-knowledge-base-best-practices.md](./personal-knowledge-base-best-practices.md) 第 21 节。
> 目标：在本机（VENTUNO Q）把 **V0.1 最小闭环** 跑通，不做任何 V0.2+ 的功能。

---

## 0. 环境事实（已实测，计划以此为准）

| 项 | 实测结果 | 对实现的影响 |
| --- | --- | --- |
| Python | 3.12.3（系统），无 pip，venv 可用 | 代码必须**零第三方依赖**（纯 stdlib），requests 也不用（用 urllib） |
| SQLite | 3.45.1，FTS5 + `trigram` tokenizer 可用 | 直接用 FTS5 trigram 支持中文子串检索 |
| 本地模型服务 | `http://127.0.0.1:8080/v1` 运行中（vlm_server，Bearer `sk-local`） | OpenAI 兼容；模型别名 `qwen3-4b`（文本）、`qwen3-vl-4b`（视觉） |
| 模型能力 | qairt/NPU：**不支持 tool calling**，上下文编译期固定约 4–8k，实测约 16 tok/s | 提示词必须小；抽取输出限 max_tokens ≤ 768；只做抽取/摘要/OCR，不做长文推理 |
| PDF 工具 | `pdftotext`、`pdftoppm`（poppler）可用；无 tesseract、无 PyMuPDF/bs4 | 文本 PDF 走 pdftotext；扫描 PDF 用 pdftoppm 渲染 PNG → qwen3-vl-4b OCR |
| 图片 | vlm_server 会自动内联 http(s) 图片 | 本地图片自己读文件转 base64 `data:` URL 上送 |

## 1. V0.1 范围

**做：**

- `inbox → raw → parse → normalize → chunk → LLM 抽取(IR) → SQLite+FTS5 → search/ask`
- 输入格式：Markdown / 纯文本 / HTML / 文本 PDF / 扫描 PDF（OCR）/ 图片（OCR）
- Knowledge IR：summary / topics / entities / claims / relations
- 检索：FTS5 trigram + bm25 排序，短查询 LIKE 兜底
- `ask`：检索 top 片段 + claims 组装上下文，本地模型作答，带来源编号

**不做（推迟到 V0.2+）：**

- Embedding / 向量检索 / Hybrid Search
- Entity Resolution（别名归并、跨文档消歧）
- Claim 去重与冲突检测（superseded_by 字段先建好但不自动填）
- Knowledge Graph、Daily digest、Memory 层、Web API、watch 常驻（V0.1 只提供手动 `compile`；`watch` 可留一个轮询占位）

**数据目录**（默认 `~/knowledge`，`KC_HOME` 覆盖）：

```
~/knowledge/
├── inbox/        # 低摩擦入口，放任何原始文件
├── raw/          # 不可变原始副本：<sha256前16位>__<原名>

## 3. 数据库 Schema（SQLite + FTS5）

```sql
documents(id PK, title, source_path, source_type, sha256 UNIQUE, content,
         char_count, lang, summary, model, created_at, compiled_at, ir_json)
chunks(id PK, document_id FK→documents ON DELETE CASCADE, ord, text, char_count)
claims(id PK, document_id FK, text, norm, type, confidence,
       source, status DEFAULT 'active', superseded_by, created_at)
entities(id PK, name, norm UNIQUE, type, aliases, doc_count)
entity_mentions(entity_id, document_id, PK(entity_id, document_id))
relations(id PK, document_id, subject, predicate, object, confidence)
compile_log(sha256 PK, document_id, source_path, status, error, compiled_at)

-- 外部内容 FTS5（触发器同步），trigram 支持中文子串
chunks_fts USING fts5(text, content='chunks', content_rowid='id', tokenize='trigram')
claims_fts USING fts5(text, content='claims', content_rowid='id', tokenize='trigram')
```

要点：

- **Incremental compilation**：编译前查 `compile_log`（按 sha256），已编译且未 `--force` 则跳过；中断的文件留在 raw，`compile --all` 可恢复。
- **Raw immutable**：inbox 文件移入 raw 后只读；重编译只动 documents/ 和 DB，不动 raw。
- **重编译幂等**：同 doc_id 先 `DELETE FROM documents`（级联清 chunks/claims/mentions）再重插；entities 的 `doc_count` 按 mentions 重算。

## 4. 各阶段实现要点

### 4.1 Parse（确定性优先，CPU first）

| 类型 | 判定 | 实现 |
| --- | --- | --- |
| Markdown/文本 | 扩展名 `.md .txt .markdown .rst .log` | 直接读 UTF-8 |
| HTML | `.html .htm` | bs4（若装）→ 否则 stdlib `HTMLParser` 去标签 |
| PDF | `.pdf` | PyMuPDF（若装）→ 否则 `pdftotext -layout`；**无文本（扫描件）** → `pdftoppm -r 150 -png` 逐页渲染 → qwen3-vl-4b OCR |
| 图片 | `.png .jpg .jpeg .webp` | 直接 qwen3-vl-4b OCR（本地文件转 base64 data URL） |
| 其他 | — | 尝试按文本读，失败则报「暂不支持」并留在 inbox |

OCR 限页数（默认前 10 页，`--ocr-pages` 覆盖），防止大 PDF 拖垮 4B 模型。

### 4.2 Chunk

- 按空行切段落，聚到 ~900 字为一块，硬上限 ~1200，块间重叠 ~120 字
- 超长段落按句号/换行再切
- 记录 `ord`，`ask` 时可按文档顺序拼接上下文

### 4.3 LLM 抽取（Local LLM = semantic compiler）

- 每次把相邻 chunk 拼成 ≤ 2500 字的批次喂给 `qwen3-4b`（温度 0.2，max_tokens 768）
- System：`你是知识编译器的语义抽取模块。只输出一个 JSON 对象，不要任何解释或代码块标记。`
- 输出契约 = Knowledge IR：

```json
{
  "summary": "1-3 句概括",
  "topics": ["..."],
  "entities": [{"name": "...", "type": "person|org|project|product|technology|place|other"}],
  "claims": [{"text": "可独立理解的论断", "type": "fact|opinion|hypothesis|decision|observation|prediction", "confidence": 0.0}],
  "relations": [{"subject": "...", "predicate": "...", "object": "..."}]
}
```

- 鲁棒解析：剥 ```` ```json ```` 围栏、取首个 `{` 到匹配的末尾 `}`；失败重试一次（附「只输出JSON」）；仍失败则降级为「仅摘要」不阻塞编译
- 限额：每文档 claims ≤ 40、entities ≤ 20、relations ≤ 30（防小模型刷屏）
- `--no-llm` 开关：只入库不抽取（纯确定性编译路径，CPU first 原则的逃生舱）

### 4.4 Persist

- `documents/<doc_id>.md`：YAML frontmatter（id/title/source/type/sha256/compiled_at）+ 正文
- DB 事务写入 documents/chunks/claims/entities/relations；claim 存 `norm`（去空白/小写规范化）供 V0.2 去重
- `ir_json` 全量存 IR —— 模型可换、可重新编译（IR 是中间表示，不是最终产物）

### 4.5 Retrieve

`search <query> [--limit N] [--scope chunks|claims|all]`：

- 词元 ≥3 字符 → FTS5 trigram 短语 OR 查询，`ORDER BY bm25()`
- 全部词元 <3 字符或 FTS 零命中 → `LIKE '%q%'` 兜底（中文两字词必需）
- 命中统一为 `{kind, id, document_id, title, text, score}` 列表

`ask <question>`：

```
检索 top chunks + top claims
→ 按文档分组、带 [n] 编号组装上下文（硬上限 ~3.5k 字符，适配 NPU 小上下文）
→ qwen3-4b：仅依据资料回答，引用 [n]，找不到就明说
→ 输出：答案 + Sources（编号/标题/doc_id/命中片段）
```

## 5. CLI 一览

```bash
./kc init                              # 建目录 + index.db
./kc add <文件|目录|URL>               # 复制进 inbox（URL 用 curl 拉取）
./kc compile [--all] [--force] [--no-llm] [--limit N] [--ocr-pages N]
./kc search "FTS5 中文检索" [--limit 10] [--scope all]
./kc ask "我的知识库里关于 X 的观点是什么？"
./kc show <doc_id>                     # 文档元信息 + claims + entities
./kc status / stats                     # inbox 待处理数 / 库统计
./kc watch [--interval 30]              # 轮询 inbox 自动 compile（占位）
```

## 6. 验收标准（Definition of Done）

1. `./kc init` 幂等，目录结构与 Schema 建齐
2. 把 `docs/personal-knowledge-base-best-practices.md` 本身 `add` + `compile`：
   - raw/ 出现不可变副本；documents/ 出现带 frontmatter 的 md
   - DB 中 documents=1，chunks≥10，claims≥5，entities≥3
3. `./kc search "Claim"` 与 `./kc search "知识库"`（两字中文，走 LIKE 兜底）均有命中
4. `./kc ask "这份文档认为个人知识库的核心是什么？"` 能给出带 [n] 来源引用的回答
5. 再次 `./kc compile` → 全部 skip（增量编译生效）；`--force` 重编译结果幂等
6. 扫描件路径：`pdftoppm` 渲染 + VLM OCR 至少跑通一张图片输入
7. LLM 服务停止时 `./kc compile --no-llm` 仍能完成确定性编译

## 8. 已知取舍

- **trigram 3 字符下限**：两字中文词靠 LIKE 兜底，召回优先于精确
- **4B 模型抽取质量**：IR 需限额 + 鲁棒解析 + 降级策略；`confidence` 字段保留但以模型自报为准（不可靠，V0.2 校准）
- **无 pip**：坚持零依赖；`requirements.txt` 仅列可选增强（装了自动启用）
- **上下文小**：`ask` 上下文硬上限 ~3.5k 字符，宁少勿溢出
